## 背景

前司有一个知识管理平台，支持本地存储、FastDFS 存储、分块上传、下载、秒传、文件分享、权限管理、在线预览等功能。离职后对相关技术实现有些遗忘，特此找到 FreeFS 这个项目进行源码阅读，吸收其中优秀设计并回忆前司技术选型。

本文按四个主题拆解：**插件化存储架构 → 上传/续传/秒传 → 在线预览 → 加密打包下载**。

## 一、插件化存储架构

各企业基建不同，toB 企业绕不开支持多种存储架构：本地存储、MinIO（S3 体系）、FastDFS、各厂在线存储，甚至企业自研。让一份代码快速切换存储架构，需要在前期就设计好扩展点，防止后期的兼容问题。FreeFS 的答案是：**SPI 发现 + 两层模板类**。

### 1.1 整体分层

```
业务层（storage-plugin-boot）
    │  只依赖 storage-plugin-core，不依赖任何具体平台
    ▼
公共接口 IStorageOperationService
    │  分片上传/下载/拿链接/改名/触发拼装
    ▼
第一层模板 AbstractStorageOperationService（平台无关，管生命周期）
    ▼
第二层模板：协议层（如 S3 协议基类，OSS/MinIO 共用）
    ▼
具体实现（本地存储 / OSS / MinIO / FastDFS ...）
```

**公共接口 `IStorageOperationService`** 声明了一个工厂方法 `createConfiguredInstance`：

- 这是 GoF 工厂方法模式的反射版：接口声明"我能造一个配置化的自己"，具体造哪个类由 `this.getClass()`（运行时的真实子类）决定。
- 为什么必须这样？因为调用方拿不到具体类。业务层手里只有 `ServiceLoader` 加载出来的接口引用，它不可能写 `new RustFsStorageServiceImpl(config)`——写死就失去解耦了。只能"问实例你自己造一个"。
- 另一个收益：同一个系统可以活多个实例，OSS 和本地各干各的，互不干扰。

接口要覆盖的方法：分片上传、下载、拿到链接、改名、触发服务端拼装（S3 协议里分片上传先进暂存区，调用 Complete 才真正拼装）。

**第一层模板 `AbstractStorageOperationService`** 实现公共接口，管生命周期，平台无关：

- 钩子约束：子类必须先校验参数再初始化。
- `ensureNotPrototype()` 防御：原型实例调业务方法直接抛异常（SPI 加载出来的是原型，配置为 null，不能直接干活）。
- 统一的日志埋点。

**第二层模板是协议层**：众多平台兼容 S3 协议（OSS、MinIO……），在协议基类里直接实现一遍，减少重复代码；子类差异部分再定义抽象钩子。

### 1.2 SPI 机制回顾

SPI（Service Provider Interface）是 JDK 内置的按约定找实现的机制：只定义接口，编译期完全不认识任何实现类；运行时由 `ServiceLoader` 去 classpath 固定位置扫描文本文件，用反射把登记的实现类 new 出来。接口的定义方/使用方与实现方彻底解耦，两边可以不在一个项目里编译。

工作过程：

1. 用当前线程的 ClassLoader 扫描 classpath 上所有 jar/目录里的 `META-INF/services/<接口名>` 文件；
2. 逐行读出类名，`Class.forName()` 加载；
3. 反射调用无参构造 `newInstance()` 实例化——这就是为什么 `AbstractStorageOperationService` 必须有无参构造，也是为什么 SPI 加载出来的实例 config 是 null（它是原型，等业务用配置重新造）；
4. 拿到一堆 `IStorageOperationService` 引用，从头到尾没有具体类名。

经典例子就是 JDBC：只要 pom 里有 `mysql-connector-j`，`DriverManager` 就能发现 MySQL 驱动——靠的是驱动 jar 里自带的 `META-INF/services/java.sql.Driver` 文件。换 Postgres 驱动，JDK 一行不用改。

**三种"多存储"实现方式对比：**

| 方式 | 做法 | 问题 |
|---|---|---|
| 直接声明 | `if (type.equals("OSS")) return new AliyunOssServiceImpl(config)` | 使用方编译期 import 所有实现，加平台必改代码 |
| Spring Bean 注入 | 全部交给容器管理 | 实现模块必须都在启动依赖里，要考虑 Bean 生命周期与配置注入 |
| **SPI** | 使用方 pom 只依赖 `storage-plugin-core`；实现 jar 在 classpath 就自动发现 | 加平台 = 扔个 jar，零代码改动 |

### 1.3 项目里的加载代码

```java
@PostConstruct
public void loadPlugins() {
    ServiceLoader<IStorageOperationService> loader =
        ServiceLoader.load(IStorageOperationService.class);

    for (IStorageOperationService prototype : loader) {
        StoragePlugin annotation =
            prototype.getClass().getAnnotation(StoragePlugin.class);
        if (annotation == null) { continue; }
        if (prototypes.containsKey(identifier)) { continue; }

        // 缓存原型实例
        prototypes.put(identifier, prototype);
        // 缓存注解元数据
        metadataMap.put(identifier, metadata);
    }
}
```

业务调用走门面：传入 `configId` 从 DB 读配置，查到原型再反射构建配置化实例。

**为什么用 SPI 而不是 Spring Bean？** 分两层看：

- *插件的发现层*：编译期解耦，插件管理模块只依赖接口模块，换个项目也能用；插件提供方和使用方可以不是一个团队，即插即用；启动时能显性看到哪些注册了，而不是等用的时候报错。
- *配置化实例层*：系统配有存储平台管理网站，可动态注册新平台——平台数量不确定，要动态可变就必须工厂 + 缓存，Spring 单例 Bean 天然不适合。

**局限也要说清楚**：这个方案不是热插拔。`ServiceLoader` 启动时扫一次 classpath，加平台仍需重启；配置化实例的多例生命周期（DB 驱动、缓存、失效重建、close 释放连接池）无论选哪种发现机制都得手写工厂 + 缓存——"灵活"不在发现层。真要不停机扩平台，得上 PF4J 或自定义 ClassLoader。

### 1.4 本地存储实现细节

分片上传：

1. **发起**：初始化，建立临时目录；
2. **传分片**：分片号直接当文件名（好处：续传查询简单，直接 `dir.listFiles()`），写入临时目录；
3. **合并**：用 `FileChannel.transferTo`，数据在内核态完成搬运，不经过 JVM 用户态缓冲区——大文件合并时 GC 压力和内存占用更小（零拷贝）；
4. 合并完删除临时目录。

分片下载：`RandomAccessFile` 随机读取，跳过规定的字节数即可实现按片下载，由下载方自己拼装。

## 二、核心链路：上传、续传、秒传

### 2.1 上传流程

1. **建任务**：一条任务一个 UUID，入库进缓存；
2. **秒传检查**：前端算好 MD5 传入，查 DB 命中后，后端还要判断**存储端文件真实存在**，才实现秒传；
3. **异步传片**：上传线程池（核心 CPU×2、最大 CPU×4、队列 200）每次上传后调用一次检查并在集齐后合并；
4. **合并**：Redis Hash 计数分片数，集齐即合并，ETag 完整性校验，合并池大小 5。

### 2.2 设计要点

- **为什么要异步？** 分片上传是 IO 密集（网络传存储端），同步做会把 Undertow 工作线程占满，并发用户一多整个应用卡死。异步化后 HTTP 线程只做"接收字节 + 提交任务"。
- **为什么要自动检测合并？** 最初是前端上传完调"上传完毕"接口，但由于网络等原因分片未处理完就触发合并——由此改成每片传完自动检测是否集齐。
- **秒传为什么还要查 `isFileExist()`？** 本地系统和存储系统没有分布式事务：存在 DB 记录还在、存储端文件已删的 timing 窗口。查一次文件存在，不存在还能删掉脏记录（**自愈**）。
- **自动合并 + 分布式锁**：前端传 N 片，每片传完都可能触发合并，不加锁会出现两个线程同时进入合并流程。锁用经典的二段检查，衍生自 Redis 锁的实现。
- **状态机**：统一的状态转换方法，允许的状态转移放进 map 里，防止非法操作。

### 2.3 下载侧对称设计

- **对称指的是接口对称**，并发策略并不对称：下载时幂等（init 创建的 UUID）写库即可——幂等可以延伸到八股。
- **限流用令牌桶**：以恒定速率往桶里放令牌，下载请求拿到令牌才能通过。
  - 默认分片 5MB，缓冲流 8KB；
  - 限速 10MB/s → 每秒放 10,485,760 个令牌；
  - 粗细两种粒度：细粒度按 8KB 申请（连续平滑），粗粒度按分片一次性申请（依靠 Guava 的欠账模型）。

## 三、多格式在线预览

策略模式：预览文件时按特定后缀类型回填模板，返回 Thymeleaf 页面；页面媒体标签按需请求流式或全量数据。

一次完整预览是"三幕式"：

**第一幕（页面层）** `GET /preview/{fileId}`

- 前处理：fileId 判空、拿文件信息、判断文件是否过大、拿到类型；
- 组装返回模板。

**第二幕（前端）** 拿着 streamUrl 二次请求

- 页面有媒体元素和脚本；
- ≤50MB：JS `fetch(streamUrl)` 一次性拿全量 → `URL.createObjectURL(blob)` → 塞给 PDF.js viewer。用 Blob 方式加载 PDF，避免 IDM（下载工具）劫持；
- \>50MB：把 streamUrl 直接给 PDF.js，由它按需分段加载。

**第三幕（流层）** `GET /api/file/stream/preview/{fileId}`（可带 Range）。

Office 类文档用 **LibreOffice 转 PDF**：第一次预览时转换，后续走缓存。转换走独立进程池——拉起 soffice 子进程，因为 LibreOffice 长期运行会 OOM，每个实例转换 200 个文件就重启。

## 四、多文件打包下载：从三段式到流式管道

### 4.1 背景

FastDFS 中的文件是加密存储的，多文件下载要打包成一个 zip。旧实现是"三段式"，共 6 次磁盘 IO：

1. 云端加密文件 → 本地磁盘；
2. 读加密文件 → 解密 → 写回普通文件；
3. 读普通文件 → 压缩 → 写 zip；
4. 发送时再读 zip。

问题：每步落盘消耗磁盘空间；大文件完全读进内存可能 OOM；速度慢。

### 4.2 业界方案调研

1. **同步流式管道**：全部改造成文件流，四级串联（下载→解密→压缩→发送），点击下载直接传文件；
2. **异步打包 + 任务化 + 进度**：用户提交下载任务，后台跑管道推送 SSE，完成后再下载压缩包；
3. **异步 + 任务化 + 进度 + 回存储**：在上一步基础上把 zip 回传存储服务器，再拿链接下载。

### 4.3 加密：信封加密

**为什么文件要加密？** 行业要求：防内部人员直接拿走文件；硬盘报废时防还原。

**信封加密（Envelope Encryption）**：

- *加密*：每个文件生成 DEK + IV + tag，组成新 KEY 加密文件；用统一的 KEK 加密 DEK，加密后的 DEK 和 IV 存数据库。
- *解密*：读 DB 拿加密后的 DEK → 用 KEK 解密 DEK → 组合 IV + tag 解密文件。
- *为什么要组合？* 如果两个 KEY 完全一致，可以异或直接解密；IV 几乎不可能重复。
- *换钥方便*：换了 KEK 只需重新加密所有 DEK，文件本体不动。
- *KEK 存哪？* 存本地，配置为不可导出。

### 4.4 压测数据

改造是渐进式的：先改 IO 落盘（流式管道），对比后再上并行压缩——相当于控制变量。

| 方案 | 100MB 批次 | 800MB 批次 | 提升 |
|---|---|---|---|
| 旧三段式 | 1.59s / 63MB/s | 11.39s / 70MB/s | 1.0x |
| 流式管道 | 1.19s / 84MB/s | 9.59s / 83MB/s | 1.2x |
| 并行 8 线程压缩 | 0.35s / 288MB/s | 1.95s / 410MB/s | **5.8x** |

**流式管道为什么只快 1.2 倍？** 拆开看耗时构成：下载落盘 6%、解密 69%、压缩 22%。流式管道只消除了磁盘 IO 那 6% 的开销，大头在计算，所以还要靠并行。

### 4.5 并行的正确姿势

解密可以按文件并行，那三个文件能同时解密、字节流同时往 zip 里写吗？

- **并行的是计算（下载/解密/压缩），串行的是写入**；
- ZIP 的字节布局是严格顺序的，不能交错写；
- 每个并行 worker 把数据算完写进**自己的暂存区**；
- 由一个合并单线程顺序写入，达到并行效果。

（加密块大小 1MB。）

其他压测数据：登录 QPS 1292，文件列表 QPS 90。

## 总结

FreeFS 这套设计里最值得带走的三个思想：

1. **发现与构造分离**：SPI 负责"找到谁"，反射工厂负责"造出带配置的实例"，原型 + 配置化实例两级设计让多平台共存成为可能；
2. **异步边界划在线程角色上**：HTTP 线程只收字节，IO 线程池干活，池参数（CPU×2/×4、队列 200、合并池 5）都是围绕"别把接入层堵死"设计的；
3. **先测量再优化**：流式管道只快 1.2x 不是失败，它精确定位了瓶颈在计算而非 IO，才有了后面并行压缩 5.8x 的正确发力点。
