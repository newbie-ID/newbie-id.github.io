TL;DR
#

我们把 mem0(LLM 事实抽取 + 向量检索的记忆层)接到了一个玩 Balatro 的 agent 上,和"全量攻略注入"做对照。训练局进步曲线清晰(三阶段均分 18.7 → 76.7 → 81.0),但 eval 换种子后掉回 38.6;挖开每次召回的留档,我们发现了一个比分数更有意思的东西:mem0 抽出的 16 条"事实"里,被高频召回的大多是比分播报,而真正有决策价值的 7 条策略教训几乎没有被检索到。这是半场报告:对照组被基础设施故障毁了,数据只有一个 arm 完整,但召回留档里的证据已经足够改变我们下一步的做法。

背景一篇带过:我们 fork 了 Evalatro(用真实 Steam 版 Balatro 评测 LLM 的 benchmark),把它从"无记忆单局评测"改造成了 Memory Arena——固定模型(gemini37-flash-high)、可插拔记忆组件,看哪种记忆结构让 agent 进步更快。上一篇讲了架构改造,这篇讲 mem0 这条分支的接入、数据、和一次真实的召回长什么样。

1. 为什么在 Balatro 上测记忆组件
#

给 agent 加记忆的论文和产品已经很多了,但常见的评测面(“多轮对话里记得用户说过什么”)和 agent 的真实工作流差得很远:agent 的记忆应该存的是带代价的经验——我上次这么做了,输了,亏掉 90 分钟。

Balatro 恰好是一个完美的记忆评测场:

  • 回合制、无实时压力,每一步决策都可以完整落盘;
  • 单局 40-90 分钟,一局内的教训(这个 Boss 克我、这套阵容后期乏力)值得沉淀;
  • 跨局经验可迁移:Boss 机制、经济节奏、“Ante 8 之后盲注要求指数上升"这些知识,换一局依然成立;
  • 分数客观:progress × legality × 100,没有裁判模型,没有口味分。

而模型的原生记忆是零:每步请求只有 system + user 两条消息,唯一的跨回合通道是一个 ≤1200 字符的 notes 字符串。记忆组件注入什么,完全由我们控制——这正是做对照实验需要的条件。

2. 实验设计
#

两个 store,其余一切相同(模型、种子池、课程表、超时):

file-full(对照组)mem0(实验组)
反思账本✅ append-only JSONL✅ 同一套,不动
整合攻略✅ 每局末全量重建✅ 同一套
注入全量攻略 + 本局笔记全量攻略 + 本局笔记 + 按局面检索的相关事实

设计意图:mem0 组不替换任何东西,只叠加一个语义检索层。这样如果 mem0 组赢,赢的就是"按需检索"这个增量;如果打平或输,也能区分是检索没用还是抽取坏了。

课程表:r1 = BENCH01 × 1 局(冷启动,先沉淀一份攻略)→ r2 = BENCH02/03 × 2 → r3 = BENCH04-08 × 3 → eval = EVAL01/02 × 2(攻略冻结,测泛化)。训练局每局结束立刻抢锁整合(先结束的车道发布的新攻略,同轮还在打的局在 ante 检查点就能用上)。

每次召回——开局一次、每个 ante 检查点一次——全部留档到 recalls.jsonl:召回时机、query、条目、相关度、注入的完整文本。这份留档是本篇所有"实际发生了什么"的证据来源。

3. 接入架构
#

mem0 是个 Python 库,我们的 runner 是 Node,所以中间加了一层 bridge:

flowchart LR
    subgraph node["Arena Runner (Node)"]
        R[局末反思] -->|"POST /add\n反思全文"| API
        M[ante 检查点] -->|"POST /search\n局面描述"| API
    end
    subgraph bridge["mem0-bridge (FastAPI, :8118)"]
        API[server.py]
        E[事实抽取 LLM\nflash-lite]
        V[embedding\nbge-small ONNX 本地]
        Q[(Qdrant 本地模式\n无服务进程)]
    end
    R --> API --> E --> Q
    M --> API --> V --> Q
    Q -->|"相关事实 top-k"| M
    API -.->|"bridge 挂 → 降级全量召回\n实验不中断"| M
几个关键决策:

  • 降级而不是失败:bridge 挂了,arena 记一条 [mem0] bridge degraded,自动退回全量召回继续跑。夜里 10 小时无人值守,任何"一挂全停"的设计都是给睡眠埋雷。
  • embedding 完全本地:bge-small 的 ONNX 走 fastembed,不依赖任何在线 embedding 服务。
  • user_id = arm 名:每个实验 arm 一套独立的记忆空间,不串味。

4. 工程踩坑(离线部署 mem0 的三个坑)
#

这套东西在一个网络环境很差的机器上落地,三个坑值得记录:

  1. 启动挂死 4 次,根因是模型下载:fastembed 默认从 hf-mirror 拉模型,镜像整晚不可达,进程卡在下载上无输出。解法是从 ModelScope 拉 BAAI 官方 fp32 ONNX,手工拼出 HF 缓存目录布局,持久化到 model-cache/,server 检测到缓存就自动进 HF_HUB_OFFLINE=1 完全离线启动(约 8 秒)。旧向量和新 embedding 的检索兼容实测正常。
  2. Qdrant 拉不动 18 个停用词文件:mem0 的 Qdrant 向量库初始化要下载一套 BM25 停用词,同样拉不动,曾把启动卡住 10 分钟以上。在 venv 里给 mem0/vector_stores/qdrant.py 打补丁禁用 BM25,退化为纯 dense 检索——对本实验无损失(我们的语料是英文短事实,本来也不靠关键词召回)。重建 venv 要重打。
  3. 网关账号池 503:事实抽取的 LLM 走共享网关,高峰期 *-nothinking 系列模型经常 503。换成 lite 系列后稳定。

这三个坑的共同教训:给记忆层做离线化的收益比想象中大——它一旦挂,挂的往往不是它自己,而是整条实验链。

对照组(file-full)那晚被一个游戏实例的冷启动故障毁掉(9 局 6 error,另一个故事),干净的 file-full 数据要等重跑——所以本篇对照结论全部悬置,只谈 mem0 组自身的现象。

6. 一次真实的召回:注入给模型的到底是什么
#

这是本篇的主体。以下全部来自 recalls.jsonl 留档,一字未改。

6.1 局面
#

train-r3 的 BENCH08 局中,Ante 5、第 11 轮,agent 的场面:4 张牌 Straight/Flush 流(Four Finger 打法),双 xMult 骨架(Constellation + Hologram),Odd Todd 提供筹码,4 个 joker 位占满、1 个空位,兜里 $4。

6.2 检索 query(代码自动从局面构造,原文)
#

Balatro game situation: phase=SHOP ante=5 round=11 money=4 blind=Big Blind
target=... jokers=[Four Fingers, Odd Todd, Constellation, Hologram]

译:Balatro 局面:阶段=商店,盲注轮=5,回合=11,现金=$4,大盲注,目标分=…,小丑牌=[四指、Odd Todd、星座、全息]

6.3 mem0 检索回来的"相关记忆”(原文,注入了 prompt)
#

- User played a Balatro run (gameId: BENCH05) that reached Ante 11 before
  losing with a score of 85.1, 425 actions, and 2 illegal actions.
- User played a Balatro run (gameId: BENCH01) that ended in a loss at Ante 3
  with a final score of 18.7.
- User played a Balatro run (gameId: BENCH04) that ...

译:

  • 用户打过一局 Balatro(gameId: BENCH05),推进到 Ante 11 后落败,得分 85.1,425 步动作,2 次非法操作。
  • 用户打过一局 Balatro(gameId: BENCH01),在 Ante 3 落败,最终得分 18.7。
  • 用户打过一局 Balatro(gameId: BENCH04)……

三条全是比分播报。 对"第 5 个 joker 位买什么、$4 怎么花"这个眼前的决策,信息量是零。

6.4 而记忆库里有的是什么
#

全部去重后 16 条"事实",人工分类:

类别条数例子
策略教训(有价值)7“Spare Trousers 和 Square Joker 在四张牌体系里提供了可靠的前中期 scaling”;“Ante 9-10 前要撤掉经济 joker,换成裸 xMult、复制和激进搜卡”;“deck 一致性达成后,Four Fingers、Juggler 这类功能牌必须在 Ante 8 卖掉换分”
比分播报(无价值)6“用户打了一局 BENCH03,到 Ante 11 输了,83.3 分”
阵容罗列(低价值)3“BENCH04 的最终阵容包括 Crafty Joker、To the Moon、DNA…”

对照 6.2 的 query:这个局面真正该被召回的是第一类里那几条——“四张牌体系"与 Straight/Flush 打法直接相关,“功能牌后期要卖"正对着"1 个空位买什么"的决策。但它们一条都没有出现;取而代之的是比分播报,以 0.67-0.74 的相关度稳定霸占检索位。BENCH01 那条 18.7 分的播报,在整晚 94 次召回里被反复命中了几十次——一条对任何局面都"泛泛相关"的文本,在向量检索里就是万能钉子户。

6.5 最终注入的 prompt 记忆区(结构,原文节选)
#

== STRATEGY MEMORY (lessons from your previous games) ==
### COMMON MISTAKES TO AVOID
- Carrying flat +Mult and Chip Jokers into late game (Ante 8+) instead of
  exponential xMult.
- Pairing anti-synergistic discard mechanics (e.g., Banner with Mail-In
  Rebate or aggressive digging).
...
== THIS RUN NOTES (your memory of the current game) ==
# Run Overview - Ante 5 (Round 11)
- **Build/Plan**: 4-card Straights/Flushes (Four Fingers). Dual xMult:
  Constellation (Planet) + Hologram (card adds). Odd Todd (chips).
...
== RELEVANT MEMORIES (retrieved for the current situation) ==
- User played a Balatro run (gameId: BENCH05) that reached Ante 11 ...

译(三段结构): “== 策略记忆(来自你之前对局的教训)== 常见错误:把平铺 +Mult/筹码小丑带进 Ante 8 之后的后期,而不是指数 xMult;把互斥的弃牌机制凑在一起(如 Banner 配 Mail-In Rebate)…… == 本局笔记(你对当前这局的记忆)== 概览 - Ante 5(第 11 轮):打法 = 4 张牌顺子/同花(Four Fingers),双 xMult:Constellation(星球卡)+ Hologram(加牌),Odd Todd(筹码)…… == 相关记忆(为当前局面检索)== (即 6.3 的比分播报)”

也就是说:真正在干活的是第一段(全量攻略,LLM 整合的产物),mem0 增量加进来的第三段,大部分时候是噪声。

7. 反思那么好,事实那么平:抽取层的失真
#

召回质量的问题往上游追,是事实抽取这一步。看一个对照。

局末反思(反思器的原文,结构化输出的一部分,EVAL01 局):

Major strategic blunder: I mismanaged joker positioning, accidentally
placing Campfire, which provides xMult, at the beginning of the joker
order. This meant its multiplier was applied to the base hand score
before Raised Fist's flat mult...

Discarding too frequently hurt Ramen's xMult multiplier. I was burning
through discards trying to draw Straights, which cost me a lot of
multiplier from Ramen.

Straights are too hard to draw in Balatro, without deck fixing, hand
size/discard vouchers, or specific jokers like Four Fingers or Shortcut.

译: 重大战略失误:我搞砸了小丑牌的位置,误把提供 xMult 的 Campfire 放在了小丑序列的最前面——这意味着它的乘数作用在 Raised Fist 的平铺 mult 之前的底分上…… 弃牌太频繁伤害了 Ramen 的 xMult。我为了抽顺子烧掉了大量弃牌次数,损失了 Ramen 的很多乘数。 在 Balatro 里顺子太难抽了——没有牌库修整、手牌数/弃牌券,或者 Four Fingers、Shortcut 这类特定小丑的话。

这段反思有具体的、可迁移的、带机制理解的教训:小丑位置影响结算顺序、弃牌次数是资源、顺子流的前置条件。而 mem0 的抽取器从同一局反思里抽出的事实,是"用户打了一局 EVAL01,在 Ante 4 输了,得分 39.7"这个量级的东西。

问题出在抽取器的角色设定:默认的 mem0 抽取 prompt 面向"记住用户的偏好和事件”(它是给聊天记忆设计的),没有人告诉它我们只想要对将来决策有用的教训,不要比分和流水账。于是它忠实地把"发生了什么"记了下来,而"学到了什么"被稀释在 16 条里只占 7 条——又因为这 7 条的措辞是具体的(提到具体卡名、具体 ante),在向量空间里反而不如比分播报"百搭”:比分播报和任何局面都有 0.7 上下的泛泛相似度。

抽取层决定了记忆的上限,检索层决定了这个上限的兑现率。两层都失真,叠加就是:注入了 568 条次"相关记忆",绝大多数是万能噪声。

8. 分析:eval 断崖的三个候选解释
#

训练 18.7 → 81.0,eval 却掉到 38.6(两局都死 Ante 4)。差距太大,必然有结构性原因,目前三个候选,各有一些(不完整的)证据:

  1. 过拟合训练种子:8 个训练种子反复出现,Boss 序列和商店刷牌固定;EVAL 种子的 Boss/牌序没见过。支持证据:eval 两局死因之一是 Boss 特效克制(EVAL01 死于 Ante 4 Boss);反对证据:样本只有 2 局,不足以下结论。
  2. 攻略泛化不足:2527 字符的攻略里相当部分是训练种子的具体经历(“BENCH05 那局的 Constellation+Hologram”),换种子后这些不适用甚至误导。recalls.jsonl 里攻略全文可查,可以做内容标注验证。
  3. 检索噪声稀释注意力:第 6 节展示的比分播报每局注入几十条次,占据 prompt 尾部(RECENCY 位置),可能干扰了攻略段的执行。这个假设最容易验证:重跑时关掉 mem0 注入或修好抽取,看 eval 变化。

三个解释不互斥,大概率都占一块。下一轮实验会分别拆开验证。

9. 下一步
#

  1. 重写抽取 prompt:明确告诉抽取器"只要决策相关的教训(什么局面该做什么/别做什么),拒绝比分、动作数、阵容流水账"——预计能把 16 条里的有效占比从 7/16 提上去,同时让有效事实在检索里更"尖锐"。
  2. 检索侧过滤:对"与任何局面都中等相关"的万能条目做降权(一个简单判据:跨局面命中的方差)。
  3. 对照组重跑:干净的 file-full arm(基础设施修复已合入),把"按需检索 vs 全量注入"的对照补上。
  4. eval 泛化拆解:换种子重跑 eval + 攻略内容标注,区分三个候选解释的占比。

10. 结语(半场报告的诚实清单)
#

这篇是半场报告,写下来的原因恰恰是中间发现:如果只看分数(训练曲线漂亮、eval 掉崖),我们会去猜"泛化问题";但挖开召回留档,真问题露出了一截——记忆管道两头都在失真,抽取把教训稀释成播报,检索让播报淹没教训。分数反映的是全量攻略(以及模型自己)在扛,mem0 的增量目前接近零甚至为负。

这大概是所有记忆系统工作的共同第一课:记忆的价值不由"存了多少"决定,而由"取回的东西对不对"决定;而"取回对不对",得靠逐次留档去看,不是靠平均分去猜。

附:可复现性
#

  • 实验 arm:gemini37-mem0-cur2,10 局完整数据与逐步动作在 SQLite(runs/moves 表);
  • 全部 94 次召回(含 query、条目、相关度、注入全文)在 memory/<arm>/recalls.jsonl;
  • 反思账本与 16 条抽取事实在 memory/<arm>/memories.jsonl 与 bridge 的 Qdrant 库;
  • 成绩快照:train 18.7 / 76.7 / 81.0,eval 38.6;对照组数据因基础设施故障作废,待重跑。
